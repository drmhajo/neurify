# دليل إعداد Supabase التجريبي لمزامنة تطبيق جراحة المخ والأعصاب

## الغرض من هذا الإعداد

سيُنشئ هذا الإعداد جدولاً واحداً داخل مشروع Supabase باسم `department_snapshots`. سيحتفظ الجدول **بلقطة JSON تشغيلية مُرقّمة** من بيانات القسم في المرحلة التجريبية. تبقى البيانات الموجودة على الجهاز في `AsyncStorage` هي النسخة المحلية الأساسية؛ ولا يشمل هذا المسار نقل ملفات الأشعة أو الفيديوهات أو المرفقات الثنائية بين الأجهزة.

> **تنبيه خصوصية مهم:** استخدم بيانات عرض وهمية فقط. لا ترفع أسماء مرضى حقيقية، أرقام ملفات، صور أشعة، تقارير طبية، أو مرفقات حقيقية إلى مشروع Supabase التجريبي أو المجاني.

| النتيجة المتوقعة | ما لن يحدث في هذه المرحلة |
|---|---|
| جدول نسخة تجريبية واحد مع رقم إصدار ووقت آخر تعديل | نقل ملفات الأشعة والدردشة والمرفقات الأصلية |
| تعطيل الوصول المباشر من تطبيقات المستخدمين | اعتماد سريري أو مؤسسي لبيانات مرضى حقيقية |
| اتصال الخادم فقط بمفتاحه المحمي | كشف مفتاح الخادم داخل تطبيق الجوال |

## الخطوة 1: الدخول إلى المشروع الصحيح

1. افتح [Supabase Dashboard](https://supabase.com/dashboard) وسجّل الدخول بالحساب الذي أنشأت منه المشروع.
2. اختر المشروع التجريبي الخاص بالتطبيق. معرّف المشروع الذي تم التحقق من اتصاله هو `zyszoiezbbrunkgscwth`.
3. من القائمة الجانبية، اختر **SQL Editor**.
4. اختر **New query** لفتح محرر استعلام جديد.

لا تغيّر أي إعدادات في **Authentication** أو **API Keys** في هذه الخطوة. لا تنسخ مفتاح `service_role` إلى التطبيق أو إلى رسالة دردشة؛ يبقى هذا المفتاح محصوراً في بيئة الخادم.

## الخطوة 2: إضافة المخطط الآمن

افتح ملف المشروع المرفق باسم `department_snapshots.sql`، ثم انسخ محتواه كاملاً إلى محرر SQL في Supabase. يجب أن يبدأ النص بالتعليق التالي:

```sql
-- Pilot-only cloud synchronization for the Neurosurgery Department app.
```

بعد اللصق، راجع أن الاستعلام يحتوي على العناصر التالية قبل تشغيله:

| العنصر | سبب وجوده |
|---|---|
| `public.department_snapshots` | تخزين لقطة JSON التجريبية ورقم إصدارها |
| `version` و`updated_at` | تتبع آخر تغيير وتبسيط معالجة التعارضات |
| `enable row level security` | تفعيل عزل الصف على مستوى قاعدة البيانات |
| `revoke all ... from anon, authenticated` | منع تطبيقات المستخدمين من القراءة أو الكتابة المباشرة |
| سياسة `service role manages pilot snapshots` | حصر إدارة السجل بخادم التطبيق فقط |

اضغط زر **Run** أو استخدم الاختصار الموضح في المحرر. لا يضيف الاستعلام أي مرضى أو بيانات تشغيلية؛ هو ينشئ هيكل الجدول والحماية فقط.

## الخطوة 3: التحقق من نجاح التنفيذ

عند نجاح التشغيل، يُفترض ظهور رسالة نجاح في محرر SQL. للتحقق اليدوي:

1. افتح **Table Editor** من القائمة الجانبية.
2. تأكد من ظهور جدول باسم `department_snapshots` تحت مخطط `public`.
3. افتح الجدول وتأكد من وجود الأعمدة التالية: `workspace_key` و`schema_version` و`data` و`version` و`updated_at` و`updated_by`.
4. افتح **Authentication → Policies** أو صفحة سياسات الجدول، وتأكد أن Row Level Security مفعّل.

من الطبيعي أن يكون الجدول فارغاً في هذه اللحظة. لا تُدخل صفاً يدوياً ولا تضف بيانات مرضى؛ سيقوم التطبيق بعد الربط بإنشاء لقطة بيانات العرض عند تنفيذ مزامنة تجريبية من حساب المشرف.

## الخطوة 4: ماذا ترسل لي بعد ذلك

بعد نجاح تشغيل الاستعلام، أرسل لي فقط العبارة التالية:

> تم التنفيذ

لا ترسل لقطة شاشة تحتوي على مفاتيح API، ولا ترسل كلمات مرور أو مفاتيح `service_role`. سأكمل بعدها ربط التطبيق بطريقة **local-first**: يحفظ التطبيق التغيير محلياً أولاً، ثم ينفذ مزامنة تجريبية عبر الخادم، مع حالة واضحة لآخر مزامنة أو العمل دون اتصال أو ظهور خطأ.

## إذا ظهر خطأ

| الرسالة أو الحالة | الإجراء المناسب |
|---|---|
| `permission denied` أو عدم ظهور زر Run | تأكد أنك داخل المشروع الذي أنشأته وبحساب مالك المشروع أو عضو يملك صلاحية تعديل قاعدة البيانات. |
| `relation already exists` | يعني أن الجدول موجود من محاولة سابقة؛ لا تحذفه. أخبرني برسالة الخطأ كما هي من دون أي مفاتيح. |
| لا يظهر جدول بعد النجاح | حدّث صفحة Table Editor وانتظر لحظات، ثم راجع أن المخطط المحدد هو `public`. |
| تشك في وجود بيانات حقيقية داخل المشروع | توقّف فوراً عن المزامنة التجريبية ولا تدخل أو تعدل سجلات إضافية؛ استخدم بيانات وهمية فقط. |

## ملاحظة قبل الاستخدام المؤسسي

هذا الإعداد مخصص للتجربة الفنية فقط. قبل ربط بيانات مرضى حقيقية، يلزم اعتماد الجهة، هوية مستخدمين مؤسسية فعلية، نموذج صلاحيات لكل مستخدم وفريق، سجل تدقيق، تشفير وإدارة مفاتيح، سياسات احتفاظ واستعادة، ومراجعة قانونية وتقنية لأمن المعلومات.
